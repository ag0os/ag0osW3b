# Decisions: seeded copy

Why the seeded copy works the way it does, with the derivation behind each choice. The obligations are in `docs/contracts/seeded_copy.md`.

### D-28. The Spanish copy lives in one file, which the seeds and a fill-the-blanks migration both read

Amended 2026-10-22 by D-36: the migration now reads a frozen copy of the file as it stood on 2026-10-19.

**Decision.** The Spanish for every seeded section is in `db/seeds/sections_es.yml`, keyed by section key. `db/seeds.rb` merges it into each section and fails on a seeded key the file lacks. The `FillSpanishSections` migration reads the same file and writes each field only where the database's field is blank.

**Derivation.** Production was seeded before there was any Spanish, and seeds are not a deploy step. Running them again would put the seeded English back over the owner's edits in `/admin`, since they upsert every field. A migration runs with the deploy, the same way `RemoveShellSettings` (D-13) carried a settings change to production. Filling only blank fields lets it run against a database the owner has already touched without overwriting anything they wrote, in either language. Keeping the copy in one file, rather than in the seeds and again in the migration, means there is one draft to correct. The migration defines its own model, so it does not depend on `Section` as the app later changes it. The owner chose the migration over pasting the Spanish into `/admin` by hand on 2026-10-19. The drafts translate the seeded English, so any English the owner changed in `/admin` before this deploy should be checked against its Spanish. Obligations: SC-7, SC-8.

### D-36. Approved copy changes reach the live site through a swap migration; the fill migration's input is frozen

**Decision.** The four changes the owner approved on 2026-10-22 (hero tagline, the first "What I do" item, the Contact intro's ending, the About bio's comma) and their Spanish reach production through `SwapSdlcCopy`, which replaces every exact occurrence of each approved old fragment with the new wording in the named stored fields, keeping the content around it, and leaves a field without the exact fragment alone. It writes only that field, not the row's timestamps, logs each target as swapped or skipped, and creates nothing; the tagline defaults change in the same PR, so a site that never saved a tagline shows the new one. The seeds are brought up to the live text, with the four changes applied. `FillSpanishSections` reads `db/migrate/20261019120100_fill_spanish_sections.yml`, a frozen copy of `db/seeds/sections_es.yml` as it stood on 2026-10-19, so the seed file can follow the live text.

**Derivation.** The owner edited several texts in `/admin` after the seeds ran, and seeds are not a deploy step: running them again would put the seeded text back over every edit (D-28). The owner chose on 2026-10-22 a deploy migration that swaps exactly the approved fragments, over re-running the seed. Requiring the exact old fragment leaves alone a field where the owner removed or changed it (a rewrite that kept the exact fragment still gets the swap), and makes a second run find nothing, since no new wording contains its old fragment. Matching is exact, with no normalisation: the live pages show each fragment, but cannot prove the stored bytes (Markdown that renders the same, such as an entity for a space, would not match). So the swap reaches a field only where the stored text matches; the migration logs each target as swapped or skipped, and after the deploy the public sentences are checked, a skipped field getting an explicit follow-up rather than a second run, since the migration is then recorded as applied. The migration defines its own models, like `FillSpanishSections`, so it does not depend on `Section` or `SiteSetting` as the app later changes them. Freezing the fill migration's input keeps what it does fixed while the seed file changes; a migration reading a file that later edits rewrite would fill different Spanish on each database. The Spanish of the new wording is a draft the owner settles in the PR. Obligations: SC-8, SC-9.
